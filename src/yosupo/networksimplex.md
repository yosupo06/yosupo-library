下限・上限付きの有向辺と各頂点の需給を指定し、最小費用 b-flow を求めます。C++20 が必要です。

```cpp
#include <yosupo/networksimplex.hpp>
```

以下の整数範囲は、現在の実装の中間計算も含めてオーバーフローを避ける**十分条件**です。許容される入力の最大範囲を表すものではありません。

## 求めるもの

頂点数を $n$、辺数を $m$ とします。辺 $e=(u,v)$ の下限を $l_e$、上限を $h_e$、単位流量あたりの費用を $c_e$、頂点 $v$ の需給を $b_v$ とします。

次の条件を満たす整数フロー $f_e$ のうち、総費用 $\sum_e c_e f_e$ が最小のものを求めます。

$$
l_e\le f_e\le h_e,\qquad
\sum_{e:\,v\to *} f_e-\sum_{e:\,*\to v} f_e=b_v.
$$

- $b_v>0$ は供給、$b_v<0$ は需要です。初期値は全頂点 $0$ です。
- 条件を満たすフローがなければ `feasible == false` を返します。
- $\sum_v b_v=0$ は実行可能性の必要条件です。満たさない入力も渡せますが、答えは実行不可能です。
- 最適解が複数ある場合、どのフローを返すかは指定されません。

| 入力の性質 | 扱い |
| --- | --- |
| 多重辺・逆向きの辺 | 使用できます。各辺に独立した下限・上限・費用を指定できます。 |
| 自己ループ | 使用できます。需給には影響せず、費用の最小化には含まれます。 |
| 非連結グラフ・孤立頂点 | 使用できます。全体の需給が釣り合っていても実行不可能な場合があります。 |
| 負の費用・負閉路 | 使用できます。負閉路にも容量の範囲で流します。 |
| 負の下限・負の上限 | $l_e\le h_e$ と整数の制約を満たせば使用できます。負の流量は辺の向きと逆向きの流量を表します。 |
| 下限と上限が等しい辺 | 使用できます。その辺の流量は固定されます。 |
| 無限容量 | 専用の表現はありません。上限・下限は有限の整数です。 |
| $n=0,\ m=0$ | 実行可能、費用 $0$、空のフローとポテンシャルを返します。 |

全頂点の需給が $0$ のときは最小費用循環を求めます。負閉路などがあると、需給を指定しなくても $0$ でないフローを返します。

## 型と共通の制約

```cpp
yosupo::NetworkSimplexGraph<Cap, Cost>
```

- `Cap` は下限・上限・流量・需給の型、`Cost` は辺の費用・内部のポテンシャルの型です。それぞれ `int` または `long long` を使います。
- `solve<TotalCost>()` の `TotalCost` は総費用の型です。`int`、`long long`、対応するコンパイラでは `__int128` を使えます。この文書では `Cap` と `Cost` の両方以上のビット幅を持つ符号付き整数型を使用条件とします。
- 符号なし整数型・浮動小数点型は、この文書の対象外です。特に `Cap` も負の需給を扱える必要があります。
- `Cost = __int128` はこの文書の対象外です。内部の `std::abs` が拡張整数型に対応するかは、コンパイル環境・モードに依存します。

頂点番号は $0,\ldots,n-1$ です。辺番号は、2 種類の辺追加関数を合わせた追加順に $0,\ldots,m-1$ です。内部の添字は `int` なので、グラフの大きさは次を満たすものとします。

$$
0\le n,\quad 0\le m,\quad
2(m+n)\le\mathrm{INT\_MAX},\quad
2(n+1)\le\mathrm{INT\_MAX}.
$$

別途、$O(n+m)$ の領域を確保できる必要があります。各関数について、[整数の安全な範囲](#integer-ranges)も満たしてください。制約違反がすべて `assert` で検出されるわけではありません。

## コンストラクタ

```cpp
yosupo::NetworkSimplexGraph<Cap, Cost> g(int n = 0);
```

$n$ 頂点 $0$ 辺のグラフを作ります。需給の初期値は全頂点 $0$ です。

**制約**

- $0\le n$。型とグラフの大きさについて共通の制約を満たすこと。

**計算量**

- 時間・空間ともに $O(n)$。

## add_vertex

```cpp
int g.add_vertex();
```

需給 $0$ の頂点を 1 つ追加し、その頂点番号を返します。

**制約**

- 追加後もグラフの大きさの制約を満たすこと。
- `solve` の呼び出し前であること。

**計算量**

- ならし $O(1)$。

## add_excess

```cpp
void g.add_excess(int v, Cap ex);
```

頂点 $v$ の需給に `ex` を**加算**します。上書きではありません。正の値が供給、負の値が需要です。

例えば、頂点 $s$ から $t$ へちょうど $F$ 流す問題は、他に需給がなければ次のように指定します。

```cpp
g.add_excess(s, F);
g.add_excess(t, -F);
```

辺の下限や初期フローによる需給の補正はライブラリが行います。呼び出し側で下限を差し引かず、元の問題の需給を指定してください。

**制約**

- $0\le v<n$。`solve` の呼び出し前であること。
- 加算後の内部の需給が `Cap` の安全な範囲に収まること。

**計算量**

- $O(1)$。

## add_edge

```cpp
void g.add_edge(int u, int v, Cap lower, Cap upper, Cost cost);
```

$u$ から $v$ へ、流量の下限 `lower`、上限 `upper`、単位流量あたりの費用 `cost` の辺を追加します。戻り値はありません。

最終的な流量は、`solve` の返り値の `flow` に追加順で格納されます。内部では `lower` を初期フローに使います。

**制約**

- $0\le u,v<n$。$u=v$ でも構いません。
- `lower <= upper`。`solve` の呼び出し前であること。
- `upper - lower`、下限による需給の補正、費用が共通の整数の制約を満たすこと。

**計算量**

- ならし $O(1)$。

## add_edge_with_flow

```cpp
void g.add_edge_with_flow(int u, int v,
                        Cap lower, Cap upper, Cost cost, Cap flow);
```

辺の条件は `add_edge` と同じで、内部で使う初期フローを `flow` に指定します。`flow == lower` は `add_edge` と同じです。

`flow` は最終的な流量の固定値ではありません。各辺の初期フローが全体として需給の条件を満たしている必要もありません。初期フローを変えても実行可能性と最小費用は変わりませんが、実行時間や選ばれる最適解が変わることがあります。

**制約**

- $0\le u,v<n$。`lower <= flow <= upper`。
- `solve` の呼び出し前であること。
- `upper - lower` と費用は `add_edge` と同じ整数の制約を満たすこと。
- 需給の補正に使う値は `lower` の代わりに `flow`。その補正が整数の制約を満たすこと。

**計算量**

- ならし $O(1)$。

## solve

```cpp
auto r = std::move(g).solve<TotalCost>();
```

指定した制約を満たす最小費用フローを求めます。`TotalCost` の省略はできません。

```cpp
template <class TotalCost>
struct FlowResult {
    bool feasible;
    TotalCost cost;
    std::vector<Cap> flow;
    std::vector<Cost> potential;
};
```

| メンバ | 意味 |
| --- | --- |
| `feasible` | 制約を満たすフローが存在するか。 |
| `cost` | 実行可能なら最小総費用 $\sum_e c_e f_e$。下限や初期フローの分も含めた全費用です。 |
| `flow` | 実行可能なら長さ $m$。追加順の各辺の最終流量。下限からの増分ではありません。 |
| `potential` | 実行可能なら長さ $n$。各頂点のポテンシャル。以下の最適性条件を満たします。 |

`feasible == false` のときは `cost == 0` と空の `flow`, `potential` を返します。この `0` を最小費用として使わず、先に `feasible` を確認してください。

ポテンシャルを $p_v$ とすると、各辺 $e=(u,v)$ について、

$$
\begin{aligned}
f_e<h_e &\implies c_e+p_u-p_v\ge 0,\\
f_e>l_e &\implies c_e+p_u-p_v\le 0.
\end{aligned}
$$

つまり残余容量が正の残余辺の被約費用は非負です。特に $l_e<f_e<h_e$ なら $c_e+p_u-p_v=0$ です。$l_e=h_e$ の辺には、この条件からポテンシャルの制約は生じません。どの頂点のポテンシャルが $0$ になるかは保証されません。

**制約**

- 同じオブジェクトに対して呼べるのは 1 回です。
- `solve` は `&&` 修飾付きなので、名前付き変数には `std::move(g).solve<...>()` と書きます。
- 呼び出すと内部状態が変更されます。呼び出し後の `g` への頂点・辺・需給の追加や再度の `solve` はサポートされません。解き直す場合はグラフを作り直してください。
- [整数の安全な範囲](#integer-ranges)を満たすこと。

**計算量**

- Network Simplex 法を使用します。実行時間は入力とピボット回数に依存し、$n,m$ のみで表す多項式時間の保証は設けません。
- ピボット回数を $P$ とすれば、時間の保守的な上界は $O((P+1)(n+m+1))$ です。辺の候補探索は 1 回 $O(n+m)$、木の更新は 1 ピボットあたり $O(n)$ です。
- 返り値を含む空間計算量は $O(n+m)$ です。

## 整数の安全な範囲

以下はすべて**数学的な整数の式**として評価してください。チェック用の式自体がオーバーフローしないよう、必要に応じてより広い型を使います。

### 容量・需給：Cap

$M_{\mathrm{cap}}$ を `Cap` の正の最大値とします。各辺について、

$$
0\le h_e-l_e\le M_{\mathrm{cap}}
$$

を満たすものとします。下限と上限がそれぞれ `Cap` に収まっていても、その差が収まるとは限りません。

さらに、グラフ構築中に内部の `excess[v]` に対して行う**各加減算の直後**の値を $[-M_{\mathrm{cap}},M_{\mathrm{cap}}]$ に収めてください。

| 呼び出し | 内部の更新 |
| --- | --- |
| `add_excess(v, ex)` | `excess[v] += ex` |
| `add_edge(u, v, lower, upper, cost)` | `excess[u] -= lower` の後に `excess[v] += lower` |
| `add_edge_with_flow(..., flow)` | `excess[u] -= flow` の後に `excess[v] += flow` |

最終的な内部の需給は、初期フローを $f_e^0$ として、

$$
b'_v=b_v-\sum_{e:\,v\to *}f_e^0+\sum_{e:\,*\to v}f_e^0
$$

です。`add_edge` では $f_e^0=l_e$ です。最終的な $b'_v$ が小さくても構築途中であふれる場合があります。自己ループでも減算と加算が別々に実行されます。また `solve` で負の `excess` の符号を反転するため、型の最小値 `LLONG_MIN` などを最終的な内部の需給として使うことはできません。

呼び出し順を考えずに確認するなら、各頂点について次の、より強い十分条件を使えます。

$$
\sum_{\texttt{add\_excess}(v,x)\text{ の各呼び出し}} |x|
+\sum_{e:\,v\to *}|f_e^0|
+\sum_{e:\,*\to v}|f_e^0|
\le M_{\mathrm{cap}}.
$$

自己ループはこの式では 2 回数えます。これらの条件で元の辺の残余容量は $[0,h_e-l_e]$、補助辺の残余容量は $[0,|b'_v|]$ に収まります。全頂点の供給量の総和まで `Cap` に収まる必要はありません。

例えば、下限が $0$ で `add_edge` を使うなら、`upper == LLONG_MAX` 自体は容量演算の制約に反しません。ただし費用の制約は別途必要で、その値も「無限」を表す特別値ではありません。

### 辺の費用・ポテンシャル：Cost

$M_{\mathrm{cost}}$ を `Cost` の正の最大値、$S=\sum_e|c_e|$ とします。下限と上限が等しい辺や自己ループの費用もこの和に含めます。次を**保守的な十分条件**として使えます。

$$
\boxed{4S+2\le M_{\mathrm{cost}}}
$$

| `Cost` | $S=\sum_e\lvert c_e\rvert$ の上限 |
| --- | ---: |
| 32 bit の `int` | $536\,870\,911$ |
| 64 bit の `long long` | $2\,305\,843\,009\,213\,693\,951$ |

各辺の絶対費用が $C$ 以下と分かっている場合は、$4mC+2\le M_{\mathrm{cost}}$ で確認しても構いません。この条件を超える入力がすべて失敗するわけではありません。

**この条件の根拠**

実装は、補助辺の費用として $A=1+S$ を `Cost` で計算します。さらに `cost + p[u] - p[v]` や、その符号反転を同じ型で計算します。

内部の木の根から各頂点への単純パスには、補助辺が 1 本、元の辺が何本か含まれます。補助辺によるポテンシャルへの寄与は $-A$ または $0$、元の辺の絶対費用の和は高々 $S$ なので、ポテンシャルは $[-A-S,S]$ に収まります。木の交換で行うポテンシャル更新の結果もこの範囲です。

残余辺の費用の絶対値は高々 $A$ なので、`cost + p[u] - p[v]` の評価途中も含めた保守的な絶対値の上界は $2A+2S=4S+2$ です。この値が `Cost` の正の最大値以下なら、補助費用、ポテンシャル、被約費用とその符号反転が収まります。

**`solve<__int128>()` だけでは内部のオーバーフローは防げません。** 広がるのは総費用の計算だけです。例えば、次は安全ではありません。

```cpp
yosupo::NetworkSimplexGraph<long long, long long> g(2);
g.add_excess(0, 1);
g.add_excess(1, -1);
g.add_edge(0, 1, 0, 1, -5000000000000000000LL);
auto r = std::move(g).solve<__int128>();
```

入力の辺費用も最適費用も `long long` に収まりますが、内部で `-5000000000000000000 + (-5000000000000000001)` を評価し、符号付き整数オーバーフローになります。また、`cost == LLONG_MIN` は辺追加時の `-cost` から問題になります。

### 総費用：TotalCost

$M_{\mathrm{total}}$ を `TotalCost` の正の最大値とします。共通の型の制約に加えて、

$$
\boxed{\sum_e\max(|l_e|,|h_e|)\,|c_e|\le M_{\mathrm{total}}}
$$

なら、各辺の費用と総費用の加算途中まで安全です。最終的な答えだけが型に収まっていても、途中の部分和があふれることがあります。

実装は `TotalCost(1) * flow * cost` として乗算するため、`Cap = Cost = long long` に対して `solve<__int128>()` を使えば、乗算と総費用の加算を 128 bit で行えます。内部の容量・費用については前の 2 節の条件が引き続き必要です。

## 使用例

頂点 $0$ から $2$ へちょうど $2$ 流します。最初の辺には下限 $1$ がありますが、指定する供給量は元の問題の $2$ のままです。

```cpp
#include <cassert>
#include <iostream>
#include <utility>
#include <vector>

#include <yosupo/networksimplex.hpp>

int main() {
    using ll = long long;
    yosupo::NetworkSimplexGraph<ll, ll> g(3);

    g.add_excess(0, 2);   // 2 供給する
    g.add_excess(2, -2);  // 2 受け取る

    g.add_edge(0, 1, 1, 3, 1);   // 下限 1、上限 3、単位費用 1
    g.add_edge(1, 2, 0, 10, 2);  // 下限 0、上限 10、単位費用 2

    auto r = std::move(g).solve<ll>();
    if (!r.feasible) {
        std::cout << "infeasible\n";
        return 0;
    }

    assert(r.cost == 6);
    assert((r.flow == std::vector<ll>{2, 2}));
    std::cout << r.cost << '\n';  // 6
}
```

この API は指定した需給をちょうど満たすフローを求めます。$s$ から $t$ への流量自体を最大化する関数や、流量と最小費用の関係を返す `slope` はありません。

`edges`, `lowers`, `excess` などは公開されていますが、内部の残余グラフや補正済みの需給を保持します。元の辺の流量は `r.flow` で取得し、これらのメンバを直接書き換えないでください。

Library Checker の入出力を含む例は [min_cost_b_flow.test.cpp]({% link test/oj/min_cost_b_flow.test.cpp.md %}) を参照してください。この例では総費用に `__int128` を使っています。
