## 関数単位の確認

`gprof` の PC サンプリングでも `SushiDeltaTrie::add` が最大でした。

| 関数 | ランダム投入 | ランダム区間・増加投入 | 全区間・増加投入 |
| --- | ---: | ---: | ---: |
| `SushiDeltaTrie::add` | 42.7% | 47.3% | 62.3% |

分母は実行ファイル内で採取されたサンプルです。共有ライブラリやカーネル内の時間は

## ハードウェア popcount の効果

通常ビルドでは `std::popcount` が `__popcountdi2` のソフトウェア呼び出しになります。
比較用バイナリだけ `-mpopcnt` を追加し、同じ入力を 3 回ずつ交互の順序で測りました。
下表は計測用タイマーを入れていないバイナリの CPU 時間中央値です。

| N=Q=200,000 | 通常の O3 | O3 + `-mpopcnt` | 時間の短縮率 |
| --- | ---: | ---: | ---: |
| ランダム投入 | 4.191 秒 | 3.964 秒 | 5.4% |
| ランダム区間・増加投入 | 5.343 秒 | 5.124 秒 | 4.1% |
| 全区間・増加投入 | 3.827 秒 | 3.729 秒 | 2.6% |

対応 CPU では有効ですが、主なボトルネックを解消するほどの効果ではありません。
ライブラリのコンパイル要件は変更していません。
400k/25k の全区間ケースでは通常版だけでも 0.540〜0.629 秒の振れがあり、
そのケースの中央値の差を安定した popcount の効果とは解釈していません。

## 次の改善候補

1. **差分 Trie の更新量と走査の重複を減らす。** 成功したクエリは履歴の削除・挿入を
   それぞれ祖先へ伝搬し、N/D/L/H の複数の集合を更新します。再帰 `add` が辿る経路の
   重複をまとめる、ノードの読み書きを減らす、という変更から測る価値があります。
   単に再帰をループに置き換えるだけで改善するかは未測定です。
2. **epoch ごとの N 要素の再ソートを減らす。** 現存キーの値順を次 epoch へ渡し、
   次の B 個の投入値をソートしてマージする方式が候補です。重複値の ID と次 epoch の
   rank を正しく作り直す必要があります。これは設計候補で、まだ実装していません。
3. **境界探索を減らす。** 更新中に `maximum_l` が必要になる回数を減らせれば、
   全体の約 9〜19% を占める処理に効きます。

配列復元はすでに小さい割合です。ハードウェアのキャッシュミス・分岐ミスの
カウンタは取得していないため、「メモリ帯域が律速」などとは断定していません。

## 測定方法と再現

`profile.py` は計測用ヘッダとドライバを一時ディレクトリへ生成します。
構築・クエリループ・復元には epoch 単位のタイマーを置きます。
クエリ内の探索・履歴編集・境界探索は 64 クエリに 1 回だけ計測します。
内側のタイマーは外側に含まれるため、`update + boundary` などと足してはいけません。

処理別割合は 3 回の wall time を合計したものを分母にしています。
探索・更新の割合は、各実行のクエリループ時間に
`その処理のサンプル時間 / クエリ全体のサンプル時間` を掛けて推定しました。
周期的なサンプリングとタイマーのオーバーヘッドを含む概算です。
200k/200k の計測版と通常版の CPU 時間中央値の差は +2.7% / -0.5% / -0.8% でした。
計測版がわずかに速い例もあり、実行変動とコード配置の影響も含まれます。

```sh
python3 experiments/sushi_rebuild/profile.py --output-dir /tmp/sushi-profile
g++ -std=c++20 -O3 -DNDEBUG -Isrc \
  experiments/sushi_rebuild/benchmark.cpp -o /tmp/sushi-profile/benchmark_base
g++ -std=c++20 -O3 -DNDEBUG -I/tmp/sushi-profile/include \
  /tmp/sushi-profile/benchmark.cpp -o /tmp/sushi-profile/benchmark
g++ -std=c++20 -O3 -DNDEBUG -mpopcnt -Isrc \
  experiments/sushi_rebuild/benchmark.cpp -o /tmp/sushi-profile/benchmark_popcnt
python3 experiments/sushi_rebuild/profile.py --output-dir /tmp/sushi-profile \
  --measure /tmp/profile_results.jsonl --repeats 3
```

全 54 サンプルを [profile_results.jsonl](profile_results.jsonl) に保存しています。
すべての入力で、通常版・計測版・popcount 版の回答と最終配列の checksum が一致しました。

関数単位の確認には次を使いました。再帰ごとの関数入口計測による歪みを避けるため、
`-mnop-mcount` で関数入口の計測呼び出しを NOP にし、PC サンプリングだけ使います。
この GCC では同オプションに非 PIE ビルドが必要でした。
`objdump` で `mcount` / `__fentry__` 呼び出しがないことを確認しています。

```sh
g++ -std=c++20 -O3 -g -DNDEBUG -pg -mfentry -mnop-mcount -fno-pie -no-pie \
  -Isrc experiments/sushi_rebuild/benchmark.cpp -o /tmp/sushi-profile/benchmark_gprof
mkdir -p /tmp/sushi-profile/gprof-random
cd /tmp/sushi-profile/gprof-random
../benchmark_gprof 200000 200000 random 0
gprof -b -p ../benchmark_gprof gmon.out
```

`increasing`、`full` も別ディレクトリで同様に測定しました。
通常のベンチマーク・PC サンプリング・ビルド・単体テストを同時に走らせていません。
