# 回転寿司クエリの再構築方式：設計と検証モデル

再構築方式の C++ ライブラリ、Python の正当性検証モデル、計測コードを保存しています。
C++ 実装は [sushi.hpp](../../../src/yosupo/container/sushi.hpp) の `SushiBatch<T>` です。
API の仕様・使用例はヘッダのコメントを参照してください。
Python モデル自体は下記の目標時間・空間計算量を満たしません。

## 対象の操作

0-indexed、半開区間 `[l, r)` に対して次を実行し、最後の `x` を返します。
配列の変更は次のクエリに引き継ぎます。

```cpp
for (int i = l; i < r; ++i) {
    if (a[i] < x) std::swap(a[i], x);
}
return x;
```

空区間では `x` をそのまま返します。重複値、負数も対象です。
Python モデルには 1 点代入はありません。C++ 版ではバッチ間の代入に対応しています。

参考：

- [元記事](https://qoj.ac/blog/qingyu/blog/4412)
- [時間軸の線分木を用いる解法](https://qoj.ac/problem/409/discussion/2701)

以下の再構築方式は会話中に提供された説明に基づきます。説明に付随する
C++ 実装は受領しておらず、今回の C++ と Python のコードは独立に実装したものです。

## 線形空間にする構成

時間軸の線分木の各ノードで、残留集合 `N`、削除集合 `D`、マージ用の
補助集合 `L, H` を考えます。現在の配列を `A0` として取り出し、各時刻 `i` に
`A0[i]` を挿入して 1 個取り出す履歴へ再構築すると、基準集合は次になります。

| 集合 | 再構築直後の基準 |
| --- | --- |
| `N, H` | 空集合 |
| `D` | ノードの時間区間に対応する `A0` の区間 |
| `L` | 右の子の時間区間に対応する `A0` の区間（内部ノードのみ） |

基準集合を個別に保持せず、`A0` に対する 1 本の静的 wavelet matrix (WM) を
共有します。各集合には基準との差分だけを符号付き Patricia Trie で持ちます。
同じ価格の要素は epoch 内で不変の ID を付けて区別します。

- 実際の個数は、WM の基準区間の個数と Trie の符号和の和です。
- 最小値・最大値の探索では WM と Trie を同じ値域ビットで同期下降します。
- 出力配列の区間極値も、前置区間と対象区間を時間ノードに分解し、
  各ノードの WM・Trie の状態をまとめて同期下降します。
- 各ビットで WM の検索を根からやり直してはいけません。
- 履歴を 1 個編集した際の集合の変化が祖先ごとに定数個である性質を利用すると、
  `B` クエリ後の差分は全体で `O(B log N)` 個です。

再構築では履歴を実行し、現在の配列を取り出します。Python モデルは priority queue を使います。
C++ 版はキーの順位順に、その挿入時刻以降の最初の空き位置へ配置します。
空き位置は successor DSU で管理します。優先度の高い要素から、その要素が使える
最も早い出力位置を埋めるので、priority queue と同じ出力になります。
差分を消すだけでなく、各要素の挿入時刻も新しい出力位置へ付け替えます。

圧縮版は各 epoch の現在の `N` 要素と、次の `B` クエリの投入値だけを
座標圧縮します。全クエリを保持する必要はありませんが、`B` 件の先読みが必要です。
一般の `B` では目標計算量は次になります（退化した小さい `N` は別途扱います）。

```text
時間：O((1 + Q/B) N log N + Q log² N)
空間：O(N + B log N) words
B = Θ(N/log N) のとき、総時間 O(N log N + Q log² N)、空間 O(N) words
```

1 クエリの `O(log² N)` は再構築込みの償却計算量です。
WM はビット列を詰め、rank の累積和を 64 bit ブロックごとに置く必要があります。
各要素・各レベルに累積和を持つ実装では線形ワード空間になりません。

### 実装上の注意

符号付き Trie の部分木の総和が 0 でも、削除 `-1` と追加 `+1` が相殺している
可能性があります。総和だけで部分木を削除せず、構造として空になった場合だけ削除します。

削除済みの基準要素の ID も、負の差分として参照され続ける場合があります。
epoch の終了までキーと ID の対応を書き換えたり再利用したりしてはいけません。

モデルでは値の降順にキーを割り当てます。履歴の priority queue は小さいキーを
取り出し、`range_min_id` は実際の値が最小の要素、すなわち区間内の最大キーを
返します。関数名とキーの向きを取り違えないようにしてください。

### 先読みをなくす整数版

座標圧縮を使わず、整数の順序を保つビット表現と epoch 内の ID を結合する方法も
検証しています。未来の投入値は不要で、epoch の容量だけ先に決められます。
値と ID を合わせたビット数を `w` とすると、目標は償却 `O(w log N)` 時間です。
基準 WM の空間は `O(Nw)` bits で、キーが定数個の機械語に収まる設定では
`O(N)` words です。64 bit 値と約 19 bit の ID なら約 83 段になり、
圧縮版の約 19 段より探索の仕事量が増えるため、速度は別に測る必要があります。

`raw=True` の検証ではテスト用にクエリを先に生成していますが、キーの割り当てに
未来の値のソートは使いません。本番のオンライン API は未実装です。

## 検証の実行

Python 3.10 以降、標準ライブラリのみを使用します。リポジトリ直下で実行します。
assert が検証本体なので `-O` は付けないでください。

```sh
python3 experiments/sushi_rebuild/check.py
```

seed は `12026` に固定しています。成功時の出力：

```text
Raw 64-bit value + epoch-ID keys: 240 additional queries matched.
OK: 11520 queries, 5463 epochs; answers, arrays, synchronous range minima and set extrema matched.
Nonempty zero-sum delta roots observed: 60019; maximum total member edits at one ancestor for one history edit: 7.
```

空配列、空区間、重複値、負数、全区間操作、非 2 冪長、64 bit ブロックの境界、
符号付き 64 bit の端点を含みます。各クエリの回答と配列を愚直解と比較し、
集合の極値と同期下降の結果も明示的な集合からの結果と照合します。

`Epoch.recompute()` は正解の集合を明示的に再計算します。
`edit()` もその集合差分から Trie を更新します。祖先への定数個の変更伝搬を
高速に実装したものではありません。明示的な集合は `O(N log N)` 個の所属を持ち、
Python のオブジェクト費用もあるため、このスクリプトを速度・メモリ測定に使えません。
観測された変更個数は証明の代わりではありません。

## 性能について残しておく情報

今回実装した C++ 版の再現手順と測定結果は [RESULTS.md](RESULTS.md) にまとめています。
処理別のボトルネックと popcount の比較は [PROFILE.md](PROFILE.md) にあります。
生データは [results_o3.csv](results_o3.csv)、計測ドライバは
[benchmark.cpp](benchmark.cpp)、反復測定用スクリプトは [measure.py](measure.py) です。
以下は提供元の報告と以前の実装についての履歴です。

提供された説明では `N=400,000, Q=25,000`、`g++ -std=c++17 -O2 -DNDEBUG`、
`B` はおおむね `N/(4 log2 N)`、単発測定として以下が報告されていました。
実装、入力、ハードウェアの情報は揃っておらず、こちらでは再現していません。
元問題の不等号の向きと本ライブラリの向きにも注意が必要です。

| 提供元の入力説明 | 時間 | 最大 RSS |
| --- | --- | --- |
| 初期値・区間・投入値がランダム | 1.26 秒 | 約 69.7 MiB |
| 昇順列に小さい値を全区間へ繰り返し投入 | 0.77 秒 | 約 74.5 MiB |

この構成は動的 Trie が小さくなる一方、WM の rank と再構築の費用が加わります。
`B` を大きくすると再構築回数は減りますが、差分とキャッシュの負担が増えます。
同一入力・同一環境で `B` の係数も変えて比較するまで、速度改善とは断定できません。

### 以前の C++ 版の復元用メモ

以前の作業環境にあった C++ の実装・テスト・ベンチマークは現在の環境には残っていません。
以下は会話に記録された設計と測定値であり、この PR のコードの性能ではありません。

- オンライン整数版 `Sushi<T>`：`query/get/set/to_vector/size`。
- 圧縮バッチ版：`sushi_batch(a, queries)` が回答と最終配列を返す。
- 値を増やす 1 点代入は長さ 1 のクエリ、減らす代入は全体再構築で対応していた。
- 各時間ノードの 4 本の Trie を、全挿入キーの 1 本の Trie と `N/D` タグ、
  個数、`L/H` の境界キーに統合していた。
- Trie は時間木の偶数高さと根だけに置き、省略した高さは子の Trie から導出。
  区間探索では候補がなくなったノードを固定された要約にまとめていた。
- この版も漸近空間は `O(N log N)`。記録上、Trie ノードは 24 bytes、
  時間ノードは 8 bytes。

以前の主測定は `N=Q=200,000`、GCC 14.2、`-O3 -DNDEBUG`。
初期値はシャッフルした順列、区間はランダム、投入値は増加させる入力で、
構築・圧縮・全クエリ・最終配列復元込み、3 回の CPU 時間の中央値でした。
オンライン版は 5.74 秒 / 57.7 MiB、圧縮バッチ版は 5.14 秒 / 64.6 MiB
（RSS は 3 回の最大値）。新方式の引用値とは条件が異なるため直接比較できません。

## 未実装の範囲

完全オンライン版と、クエリ列の途中に挟む 1 点代入は未実装です。
C++ 版の 1 点代入は `apply` 呼び出しの間で行えますが、`apply` 自体には
配列の再構築コストがあるので、これを毎回 1 クエリずつ呼んでも
オンラインの `O(log² N)` 処理にはなりません。
